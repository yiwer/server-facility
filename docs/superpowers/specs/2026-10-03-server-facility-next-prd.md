- 状态：任务拆分已确认并发布为本地 tickets；本文作为实施依据，不代表代码已改造或新 ADR 已接受。
- 目标用户：构建 Spring Boot 应用的 coding agent，以及审核、维护和部署应用的开发者。

## Problem Statement

### 用户的问题

server-facility 最初希望让 agent 快速构建 Java Spring Boot Web server，但当前交付物主要是一份设施库。agent 仍要自行决定应用如何启动、业务如何组织、认证和数据库如何接入、怎样验证生成结果，以及失败和重试意味着什么。调用工具类所需的代码变少，并不等于一个业务能力更容易被正确交付。

现有库包含值得保留的工程资产：显式错误、错误与本地化分离、自动装配、架构测试，以及设计决策记录。但部分接口把状态、依赖和运行保证隐藏在静态门面、隐式降级与全局拦截中。应用维护者难以仅从调用点判断锁是否真正生效、缓存是否兑现 TTL、幂等是否隔离业务与身份、异步结束后上下文是否干净、下载是否被完整缓存。

用户需要的结果是：agent 沿着一条清晰的默认路径，交付可以独立构建、运行、验证和维护的应用；审阅者能够识别业务边界、失败语义和资源约束，而不必先掌握一套设施库内部协议。

### 事实基线与证据边界

| 维度 | 研究时观察 | 对本 PRD 的影响 |
|---|---|---|
| 产品形态 | 单一 Maven 库，29 个顶层功能包，尚无完整可运行应用模板 | 应用模板是新增产品能力，不把数据库、认证的缺席描述为旧库缺陷 |
| 平台 | Java release 21、Boot BOM 3.5.10 | 需要完成真正的 release 25 编译和平台迁移 |
| 工程资产 | 11 个自动装配类、23 份编号 ADR、5 条 ArchUnit 规则 | 保留质量门与历史设计理由，变更语义时补充替代决策 |
| 已验证基线 | JDK 25.0.4.1、Maven 3.9.16 执行原配置，1196 项测试通过；当时 release 仍为 21 | 只能作为现状证据，不能用来宣布 JDK 25 字节码或 Boot 4 迁移成功 |
| 行为研究 | 消费者探针复现幂等、身份清理、响应缓存、锁与资源相关反例 | 将有价值的反例转成外部行为回归，不以旧单测全绿代替契约正确性 |

### 产品目标

1. **可交付**：从模板得到一个独立应用，并完成带认证、持久化、校验、错误处理的业务垂直用例。
2. **容易写对**：新增业务主要修改所属业务 Module；调用者无需协调全局注册器、线程上下文、内部锁协议和响应缓存。
3. **保证可见**：接口明确身份范围、失败、时限、资源所有权和一致性；必需保障缺席时确定失败。
4. **默认路径少**：JDK、Spring 和成熟库负责标准能力；项目只维护确有价值的策略与深 Module。
5. **可持续升级**：平台、依赖、公共协议、持久数据和模板副本都有可检查的迁移方式。

不预设吞吐量提升或 agent 效率提升百分比。先建立可重复测量的任务基线，再用数据判断改造收益。

## Solution

### 产品定义

采用研究中的方案 C：一个推荐的 Spring Boot 应用模板，配合少量运行时能力。吸收方案 A 的精简原则；仅在真实消费者证明稳定复用价值后，采用方案 B 的独立 starter 发布方式。

模板承载应用入口、业务示例、数据库迁移、认证配置、运行验证说明和部署说明。应用拥有业务授权、不变量、事务和业务结果。运行时只承载应用不应重复实现、且接口能够隐藏实质复杂性的通用策略。标准框架继续拥有依赖注入、执行器生命周期、JSON、HTTP 客户端、缓存、日志与观测。

“深 Module”的判据是：调用者通过清晰的接口获得完整保证，不需要在模块外协调隐藏步骤。“Seam”只为真实的替换或验证需要建立，不为未来可能存在的实现预先增加接口。

### 首版场景

| 场景 | 首版交付 | 交付边界 |
|---|---|---|
| 内部管理与关系型 CRUD API | 一个带认证、授权、校验、分页约束、数据库迁移和错误契约的业务示例 | 单体 MVC，同步应用服务；一种关系数据库和一种数据访问方案 |
| 对外创建或变更命令 | 在同一示例中展示可重试命令、同库事务与可恢复结果 | 保证限于明确的事务模型，不扩张为跨系统通用 exactly-once |
| 外部服务聚合 | 类型化 HTTP Adapter 的接入说明与消费者契约验证 | 使用 Spring 标准客户端，明确超时、预算和重试适用条件 |
| 文件导入导出 | 修正继续支持的旧能力之资源与错误契约，提供独立消费验证 | 不将完整 documents 平台或新的业务导入功能设为首版前置条件 |

### 成功判据

- 全新环境在声明的先决条件满足后，按文档完成构建、启动、调用、测试和打包，不需要临时修改库源码。
- 新增一个业务端点和一个持久化命令，不需要修改通用运行时或全局错误大枚举。
- 普通请求不会因启用其他能力而无界缓存整个响应；错误和幂等重放不会暴露其他身份的数据。
- 同一业务命令在并发、提交后断连、进程重启和双实例情况下，得到设计承诺的业务效果与可解释的返回结果。
- 目标依赖组合通过实际编译、测试发现、打包和独立消费验证；不能只以版本号更新或构建退出码为完成证据。
- 保留的每项公共能力都有清楚的所有者、资源约束与失败规则；退出的能力有可执行迁移说明。

## User Stories

以下用户故事使用“作为某角色，我希望某能力，以便获得某收益”的格式；括号中为对应需求。

1. 作为应用开发 agent，我希望从一个默认模板得到可启动的应用，以便从业务任务开始工作。（FR-07）
2. 作为应用开发者，我希望只安装声明的 JDK 和场景所需环境就能构建项目，以便不依赖某台机器的 Maven 配置。（FR-01、FR-07）
3. 作为维护者，我希望所有直接依赖和构建插件都有版本来源与升级结果，以便检查平台的一致性和可维护性。（FR-01）
4. 作为库消费者，我希望发布物能在独立应用中被正常引用，以便不依赖仓库内部测试类或隐式 classpath。（FR-02）
5. 作为应用开发 agent，我希望沿业务 Module 增加端点、命令和测试，以便业务改动保持局部且容易审阅。（FR-08）
6. 作为应用开发者，我希望有一个真实持久化示例，以便理解事务、数据库约束、迁移和错误之间的关系。（FR-07）
7. 作为审阅者，我希望接口说明失败、时限和资源归属，以便从调用点判断是否兑现业务需要的保证。（FR-05、FR-08）
8. 作为 API 消费者，我希望收到真实状态码、稳定错误码和安全的错误详情，以便正确处理成功、校验失败、冲突和系统故障。（FR-03）
9. 作为运维人员，我希望通过 trace 关联内部原因与外部错误，以便排查故障而不向客户端暴露内部异常。（FR-03）
10. 作为应用用户，我希望未认证和无权限请求被一致拒绝，以便身份边界不取决于错误发生在哪一层。（FR-03）
11. 作为应用维护者，我希望开发身份只在明确的本地配置下生效，以便生产缺少身份配置时不会自动放行。（FR-03、FR-07）
12. 作为 API 消费者，我希望请求提交后连接断开时可以使用同一请求键重试，以便取回已完成的业务结果。（FR-04）
13. 作为业务负责人，我希望同一身份和操作下的请求键不能对应不同命令，以便错误重试不会产生含糊的业务效果。（FR-04）
14. 作为应用用户，我希望幂等记录按身份、租户和操作隔离，并在重放前重新检查授权，以便结果不会被其他调用者取得。（FR-04）
15. 作为运维人员，我希望并发请求、等待超时和处理中状态可以区分，以便不会把暂时未知的结果当作业务失败重做。（FR-04）
16. 作为业务负责人，我希望响应保留期结束不会自动允许重复执行旧命令，以便清理历史结果不破坏业务唯一性。（FR-04）
17. 作为下载接口消费者，我希望普通下载和流式响应及时输出，以便不会被全局幂等机制完整缓存在内存中。（FR-03）
18. 作为应用维护者，我希望同步、异步、超时和异常请求结束后都清理身份与观测上下文，以便下一请求不会继承前一请求的数据。（FR-05）
19. 作为库消费者，我希望多个应用上下文能独立创建和关闭，以便测试、重载或嵌套上下文不会相互破坏。（FR-05）
20. 作为业务开发者，我希望请求必需的锁或后端缺席时操作被拒绝，以便不会在保证消失后继续执行。（FR-02、FR-05）
21. 作为缓存使用者，我希望声明的 TTL 和容量被兑现，以便运行环境变化不会悄悄改变数据时效和内存占用。（FR-05）
22. 作为 API 维护者，我希望限流使用可信身份和明确预算，以便非法成本或大量新键不会恢复其他请求的额度。（FR-05）
23. 作为应用开发者，我希望默认 ID 不需要隐式节点协调，以便多个实例不会由于默认配置生成相同标识。（FR-05）
24. 作为外部系统集成开发者，我希望客户端调用保留必要状态、头和失败信息，以便在预算内决定是否重试或返回未知结果。（FR-08）
25. 作为文件接口开发者，我希望摄入流程同时控制大小、类型、名称和清理，以便不必在多个工具类之间拼接资源规则。（FR-06）
26. 作为导入功能开发者，我希望表格处理具备行列预算和可定位的错误，以便大文件或坏数据不会造成无界缓冲和静默丢失。（FR-06）
27. 作为文件接口消费者，我希望 MIME 探测不会意外丢失输入内容，以便后续保存和摘要计算得到完整原文。（FR-06）
28. 作为应用开发者，我希望自己提供的合法配置和 bean 能按约定覆盖默认行为，以便不必依赖全局静态注册表。（FR-02、FR-08）
29. 作为现有 API 消费者，我希望收到兼容变化说明和替代用法，以便能够迁移错误格式、JSON 类型和旧静态调用。（FR-09）
30. 作为数据维护者，我希望旧 ID、密文与已持久化协议仍有明确读取策略，以便升级不会隐式损坏已有数据。（FR-09）
31. 作为应用维护者，我希望知道模板版本与运行时版本，并能按差异升级，以便不会重新生成后覆盖业务代码。（FR-09）
32. 作为项目维护者，我希望测试主要断言消费者可观察行为，以便内部实现可以变化而不损坏公开承诺。（FR-10）
33. 作为框架负责人，我希望用固定任务比较旧版与新版的 agent 体验，以便判断哪些抽象真正减少了纠错和上下文成本。（FR-10）
34. 作为共享能力维护者，我希望只有真实的第二个消费者证明共性后才提取新模块，以便避免维护没有用户的扩展体系。（FR-11）

## Implementation Decisions

本节是本 PRD 推荐采用的设计约束。涉及现有已接受 ADR 的变化，须在相应实现批次先登记 superseding ADR；本文件不直接改写历史决定。

### D-01 产品结构与所有权

- 首版是一条默认应用路径；不将 29 个包一一拆成 artifact，不同时建设通用生成平台。
- 纯核心保留少量值类型与错误语义，不依赖 Spring 和服务定位器。Web 策略通过模板配置或经过验证的少量装配提供，artifact 数量由实际复用决定。
- 应用按业务组织 HTTP Adapter、应用操作、持久化协作者和测试。业务 Module 负责授权、不变量、事务与结果；不强制 Service/Impl 双类、空层级或通用 CRUD 基类。
- 文件、Excel 等重依赖能力按需使用，不由默认 Web 路径隐式引入。完整 documents Module 属于 FR-11。
- 旧设施库是迁移资产。对继续支持的能力修正契约；对退出的能力提供替代和弃用说明，而非为了新结构重写每个包。

### D-02 平台与依赖政策

| 层次 | 研究快照中的候选目标 | 实施约束 |
|---|---|---|
| Java | JDK 25，release 25，class major 69 | 唯一 release 来源，默认关闭 preview；固定选定发行版的补丁与构建环境 |
| Spring 平台 | Boot 4.1.1 BOM；关联 Framework 7.0.9、Security 7.1.1 | 采用一个受支持的主平台线；BOM 管理的版本默认不单独覆盖 |
| JSON 与测试 | Jackson 3.1.5、JUnit 6.0.3、ArchUnit 1.5.1 | 检查公共类型变化、配置生命周期和测试引擎实际发现结果 |
| Maven 与工具 | Wrapper 固定 Maven 3.10.0；Compiler 3.16.0、Surefire 3.6.0、JaCoCo 0.8.15 | 校验分发下载；独立管理构建插件，不能误认为导入 BOM 会管理插件 |
| 非 BOM 能力 | Tika 4.1.0、jsoup 1.23.2、POI 5.5.1 | 按行为回归后升级，不以编译成功替代流位置、格式和资源契约验证 |

这些数字来自 2026-10-03 的研究快照，不是永久“最新版”承诺。实施开始时复核发行状态和兼容性，锁定完整依赖账本；所有原有直接依赖、annotation processor、显式插件都必须有升级、删除或保留理由，完整条目以研究矩阵为输入。

Boot 3.5 的维护版允许作为区分 JDK 与框架迁移故障的中间提交，不作为新的长期平台。Boot 3/Jackson 2 与 Boot 4/Jackson 3 采用分离发布线，不宣称同一二进制兼容两个主版本。普通库仍发布普通 jar；只有应用产物使用应用打包方式。

Jackson 迁移必须覆盖不可变 builder、MVC 与注入 mapper 的一致性、泛型类型和错误通道。保留 Jackson annotations 的实际坐标，删除已经并入 Jackson 3 的冗余模块，不执行无差别包名替换。时间、枚举、long ID、null、未知字段等 wire 行为采用消费者样本验收。

### D-03 模板的单一默认路径

- 默认 Spring MVC + 同步应用服务。执行器由 Boot 管理；虚拟线程按阻塞 I/O 场景显式启用并验证资源预算，不作为无条件开关。
- 持久化示例推荐 PostgreSQL + Flyway + JdbcClient，保持 SQL 和事务可见。首版不同时提供 JDBC、JPA、MyBatis 多套模板；更换默认方案需要记录具体业务收益。
- Schema 初始化由一种迁移机制负责；业务表、约束与命令结果记录随迁移交付。测试采用与示例相同类型的数据库。
- 列表端点定义页码、页大小及偏移预算，非法或超限输入返回确定的 400 错误；排序键由端点允许集映射到持久化字段，不接受任意 SQL 片段。列表响应结构与空结果语义保持稳定，不另建通用查询 DSL。
- API 模板采用 Spring Security JWT resource server，生产显式配置可信 issuer 和 audience；业务操作执行当前授权。开发身份仅在明确命名的本地配置中提供，不因缺配置自动成为匿名业务用户。
- 基础构建只需声明的 JDK 与网络条件；数据库验证或带数据库启动额外声明容器环境或可用数据库。说明开发配置、环境变量、健康检查、启动、打包和部署步骤，但本 PRD 不包含实际部署操作。

### D-04 HTTP 与错误协议

- 新模板成功返回业务 DTO，失败采用真实 HTTP 状态与 RFC 9457 ProblemDetail，提供稳定业务 code、安全 detail、必要字段错误和 traceId。
- 内部异常 cause 保留在服务端日志；生产响应不得直接复制任意异常消息、栈、SQL 或凭据。
- Filter、Security 和 MVC 的错误保持同一外部策略，覆盖 401、403、参数校验、资源不存在、冲突、限流和内部故障；遵守状态对应的必要响应头。
- 普通下载、SSE 和非目标接口不进入完整响应缓存。成功创建的 Location 等业务必要信息应在重试结果中保持一致。
- 旧 HTTP 200 + BaseResponse 仅通过明确兼容路径继续服务旧客户端；迁移时同步契约测试。身份隔离错误、必需保障缺席或无界资源行为不以兼容开关保留为默认。

### D-05 业务命令幂等

- 公开入口是业务 Module 的命令操作，输入包含可信 actor、请求键和命令；调用方不负责协调内部 claim、锁、缓存和提交步骤。
- 命令身份至少包含适用的 tenant、actor、operation 和 request key。为规范化命令计算 fingerprint；同键同内容可恢复结果，同键异内容明确冲突，不同身份和操作相互隔离。
- 每次读取或重放前执行当前授权，不把持有请求键当作获得业务结果的权限。
- 默认采用同库事务：唯一命令键、业务写入和可恢复业务 receipt 原子提交。事务回滚不留下“成功结果”；提交后断连可凭相同键恢复。
- 相同键的竞争受等待预算限制；其他事务完成后读取结果或重试，超时返回明确定义的处理中/可重试结果，不无限等待，也不据此断言业务未发生。
- 记录存储以业务结果为中心，至少明确作用域、fingerprint、结果引用或可恢复结果、时间和保留策略；不默认存储全站任意 HTTP 字节响应。
- 可重试的基础设施失败、确定的业务拒绝和已提交结果需分别定义保存策略。响应数据保留期与业务键保留期分开；receipt 被清理后，旧键也不能直接获得重复执行授权。
- 独立 claim/lease 只用于继续支持的旧协议修复或真实事务外需求。此时 owner/generation 条件更新防止旧执行者覆盖新状态，但不能保证旧执行者停止副作用；业务条件写或外部幂等协议另行负责。
- 跨外部系统不提供通用 exactly-once 保证。涉及未知远端结果时，接口必须表达未知与恢复途径。

### D-06 运行时、资源和生命周期

- 新推荐路径使用构造器注入、原生 builder 和 Spring 生命周期，不引入 SpringContextHolder 等静态服务定位器。旧路径继续支持期间，生命周期归属必须正确。
- 外部 HTTP Adapter 注入 Boot 管理的 RestClient.Builder 或使用标准 HTTP service 配置，继承宿主 JSON、customizer 与观测策略。不同第三方的认证头、超时和客户端定制隔离；超时、4xx、5xx 与非法响应分别表达。有副作用的请求默认不自动重试，显式重试必须说明业务幂等依据与总预算。
- 同步、异步、错误派发与超时均明确上下文安装和清理。多上下文不能因另一上下文关闭而丢失自身能力。
- 异步调用使用声明的执行器，明确关闭责任、截止时间和协作式取消。传播原始错误类别，不把断言或普通异常误报成超时，不在组合中延长已有 deadline。
- 本地锁与分布式锁分别命名，等待时长与持有期限分开。缺少操作所需的实现时，不执行受保护业务；本地锁不宣称跨实例保证。
- 缓存采用 Spring Cache 与明确后端。需要 TTL/容量的配置必须由实现兑现或在使用前拒绝，不能悄悄退化为无过期 Map。
- 限流明确身份来源、计费单位、作用范围、容量和故障策略。拒绝非法 cost；新增键不能通过清空全部状态恢复其他主体额度；代理 IP 只有在可信代理配置下使用。
- 默认 UUID；确需 SnowId 时显式配置节点分配协议及有界时钟回退行为，取消生产节点 0 的静默兜底，不改写存量 ID。
- 所有摄入、重放、缓存和并发路径必须有已声明预算或明确禁用。具体默认值在相应 ADR 中给出理由与边界测试，不用无依据数字伪装容量规划。
- SLF4J、Micrometer 和宿主负责日志与观测，逐步退出静态二次日志管线；纯脱敏函数只是辅助，敏感输出优先使用字段白名单。

### D-07 文件与表格能力

- 对继续支持的上传入口集中约束大小、允许类型、可信存储名称和临时资源清理；区分展示名与存储键，不接受路径越界或符号链接逃逸。
- 声明输入流关闭责任、探测后的流位置、失败时的部分结果和输出覆盖规则。MIME 探测不等于内容安全审查。
- Tika 升级后，完整摄入结果的摘要必须与原始输入一致；对可 mark 与不可 mark 的输入都验证，不允许探测消耗前缀后静默保存残缺文件。
- CSV 采用成熟解析能力，严格与 legacy 方言显式区分；面向电子表格的软件导出定义公式策略。业务字段映射与必填规则仍由应用拥有。
- Excel 与 CSV 定义字节、行、列、错误收集及临时空间预算；大输入不得默认全量装入内存。可保留有明确上限的小数据便利入口。
- ZIP 处理明确部分失败、输出是否位于输入树、重复名称和资源释放，不能把部分成功统一伪装成完整成功。
- 首版修复已有能力的这些契约；只有真实导入场景和复用证据出现后，才提取统一文件生命周期 Module。

### D-09 兼容、发布与模板升级

- 建立消费者与公开契约清单后确定弃用窗口；当前没有足够证据指定旧坐标的停止支持日期。
- 记录 Jackson 公共类型、JSON wire 行为、HTTP 错误格式、CSV 方言及静态入口迁移。旧接口的已接受语义不因目录调整而被暗中修改。
- 加密策略变更先提供旧格式和旧 KDF 参数的读取路径，再改变新写入策略；不得通过修改全局迭代次数使历史密文不可读。
- 模板版本与运行时版本分别记录。升级通过明确差异和迁移说明完成，不重新生成并覆盖业务源码。
- 新运行时公共接口必须有消费者验证；提取新 starter 或 Adapter 还需第二个真实消费者证明复用价值。测试 fixture 能验证兼容，不能冒充真实复用需求。

## Testing Decisions

### T-01 验收 Seam 与测试原则

主验收入口是**独立生成/消费应用的 HTTP 行为**：请求、状态、头、响应体、数据库中可观察的业务效果以及资源是否最终释放。为隔离业务事务和错误语义，可在同一业务 Module 的公开操作补充验证；这是辅助入口，不要求每个内部协作者都建立测试接口。

自动装配沿用现有 ApplicationContextRunner 类测试的边界，验证公开配置与依赖组合；库发布兼容通过普通发布物被独立应用引用验证。纯值类型、受控文件接口等没有 HTTP 使用场景的能力，继续在已有公共 Interface 验证，不为了统一测试而增加人为 HTTP 包装。

用户在任务拆分阶段明确要求：底层脚手架的测试用例、场景测试、接合测试和极端使用情况应全面覆盖。上述公共入口共同构成分层验证面，不用单一 HTTP 冒烟或库内部单测替代其他必要证据；具体任务划分已由用户确认并发布为本地 tickets。

好的测试断言对消费者有价值的行为，允许内部类拆分、算法与协作者更换。并发测试使用受控时钟、屏障和可解释故障注入，避免依赖随机 sleep；事务、数据库约束和跨实例行为使用真实同类型数据库验证。文件测试包含外部独立样本，不只做同一实现写出再读回。

现有先例包括 JUnit 行为测试、五条 ArchUnit 约束、自动装配条件验证、覆盖率与依赖分析门，以及研究期间的消费者反例。旧测试若仅锁定被明确替代的内部实现，应迁移到新契约；不以保住固定测试数量为目标，也不无理由削弱质量门。

### T-02 可验证验收条件

| AC-03 首次成功路径 | 按声明先决条件完成实例化、构建、数据库迁移、启动、认证调用、业务写入、读取、打包；重启后业务数据保留；列表非法页码、超限大小/偏移及未知排序键返回 400，响应结构稳定；无需修改 runtime | 一次从干净环境执行的完整记录，持久化/分页边界测试与运行说明 |

| AC-07 生命周期 | 多 context 的关闭、父子关系和刷新不相互破坏；SYNC/ASYNC/ERROR、Filter 短路、Callable、DeferredResult 和超时后身份/trace 无残留；执行器使用与关闭责任可观察，异常不会被错报为超时 | 真实容器生命周期回归、相邻请求隔离和执行器/截止时间测试 |
| AC-08 运行时保证 | 必需锁缺席时受保护业务没有执行；TTL/容量兑现或明确拒绝；非法限流 cost 被拒绝，key churn 不恢复他人额度；UUID 默认；SnowId 无隐式节点兜底且时钟回退有界 | 公共接口行为测试、可控时钟/预算测试与配置失败记录 |
| AC-09 装配失效策略 | 开启但缺少必需 Adapter 的能力在接受业务操作前失败；可选能力关闭不影响其他能力；Filter 单次入链且顺序正确；配置不被静态注册表覆盖 | 配置矩阵、消费者启动及请求链测试 |
| AC-10 文件与表格 | 大小/类型/名称同时生效，短文件名不产生未声明失败，路径及链接不逃逸；探测后原文摘要一致；资源成功/失败均清理；CSV 方言/公式、Excel 稀疏行和预算、ZIP 部分失败符合协议 | 可/不可 mark 输入、限额边界、异常注入、独立 CSV/Excel 样本与临时资源检查；范围限于继续支持的能力 |
| AC-11 结构与局部性 | 新推荐路径无服务定位器和全局无界响应缓存；新增业务端点/命令集中在其业务 Module 及迁移/测试，不改通用核心；29 包均有保留、改造、弃用或退出记录 | 一个真实新增用例的改动清单、架构规则、包处置与公开 API 账本 |
| AC-12 迁移可执行 | 旧客户端错误协议、JSON 样本、CSV legacy、旧 ID 和密文读取有处理方式；弃用先有替代；模板与 runtime 版本独立可追溯；升级不覆盖业务改动 | 消费者盘点、迁移样例和契约回归、superseding ADR、版本与变更说明 |
| AC-13 全面测试与原质量门 | 目标字节码下编译、测试发现、覆盖率、架构和依赖分析均通过；每项公共契约和关键接合均有正常、边界、失败及资源清理证据；不因升级静默漏掉测试或放宽依赖 ignore | 指令/行覆盖率至少 88%、分支至少 75%；契约—场景—测试—执行结果追踪无空项；五条既有架构规则保持约束或被说明等价替代；报告测试发现差异 |
| AC-14 agent 体验 | 以固定任务实测旧版与新版，记录完成、一次通过、人工纠错和上下文读取量；首版支持的任务均有可验证产物，不声称未经测量的收益 | 冷启动、加端点、改错误、接外部调用、已有文件能力接入五项任务的环境、任务文本、结果与纠错记录；文件项不要求新建 documents 平台 |
| AC-15 外部 HTTP | 宿主 customizer、JSON 与 trace 在实际请求生效；两个第三方的认证头与超时互不污染；超时、4xx、5xx 和坏响应可区分；有副作用的请求默认不会自动重试，显式重试遵守幂等依据和总预算 | 注入宿主配置的消费者应用与受控外部服务测试，核对实际请求次数、头、错误和截止时间 |
| AC-16 扩展提取 | 每个新共享模块有两个真实消费者的共同需求，公共接口不暴露消费者必须协调的内部协议；新增后端有对应故障模型验证 | 独立扩展提案与消费者证据，仅适用于 FR-11 |

### T-03 资源与性能验收口径

首版不制定无依据的 QPS、延迟或内存绝对指标。每项继续支持的资源能力必须登记限额、并发预算、溢出结果、释放责任和观测方式；验收覆盖低于、等于、超过限额与失败清理。流式响应必须在完整生成前可消费，内存占用不因响应长度而无界增长。后续容量目标由真实部署负载测量确定。

### T-04 底层脚手架的全面测试要求

- 每张实现 ticket 同时交付测试、契约说明与运行证据。测试不是另一个最终阶段；最终发布票只验证组合和收敛已归属的场景。
- 建立公共契约到用例、场景、接合点、极端输入及执行结果的矩阵。29 个功能包、FR-01–FR-10 和 AC-01–AC-15 全部有负责票；FR-11/AC-16 明确为条件扩展。
- 用例层覆盖成功、空/null 约定、非法输入、边界、异常类别、资源所有权和不变量。适合的解析、状态机、计算与格式使用带固定种子及可重放失败输入的性质测试或有界模糊测试。
- 接合层覆盖配置与依赖、Security/Filter/MVC、线程与上下文、业务事务与 receipt、序列化与 HTTP、限流与重放、文件探测与持久化、解析器与临时资源。对已知高风险组合逐项列举；其余配置采用有理由的组合取样，不声称穷举无限配置空间。
- 场景层使用真实 Servlet 容器、实际 HTTP 请求、同类型数据库、独立消费产物和双进程实例。外部故障用受控服务、屏障及提交点注入；mock 不能成为事务、派发或装配正确性的唯一依据。
- 极端情况至少涵盖限额前/等于/超过、溢出、非法编码、慢读慢写、断流、超时/取消、时钟回拨/冻结、同键竞争与键洪泛、提交前后故障、重启、反复开关上下文及资源回收。只在受控临时环境构造，不通过耗尽宿主内存或磁盘模拟。
- 快速确定性测试随每次变更运行；相关集成测试随负责票运行；合入和发布执行平台矩阵与关键接合；有界长稳/种子测试记录时长、规模、随机种子、预算和结果。隔离不稳定测试须有责任票与恢复条件，阻断项不得因重跑偶然通过或静默跳过而放行。
- 不要求无意义的百分之百行覆盖。覆盖率保留为门槛，合同语义、接合场景、故障恢复和资源预算分别提供证据；高风险安全、一致性或资源场景缺证据时，首版不得发布。

## Out of Scope

- 首版不建设多模板生成平台，不将每个功能包拆成发布模块，也不同时支持多个 Spring 主平台于同一二进制。
- 不默认引入微服务、响应式全栈、Redis、分布式锁、消息总线和多后端编排；需要时按具体故障模型另立扩展。
- 不建设通用 BaseService/BaseController、万能 Repository、反射领域映射框架或另一套 DI、日志、trace、Async DSL。
- 不建设身份提供商、JWT 签发系统、KMS 或完整审计平台；模板集成标准认证与观测能力。
- 不提供通用跨系统 exactly-once 保证，不将 owner CAS 解释为业务副作用不可重复。
- 不在本次首版强制构建完整文件平台、引入 Modulith/MapStruct/JSpecify，或改变 Result 的 null/Unit 模型。
- 不为了“清理”而未经消费者盘点立即删除公共 API，不重写历史 ADR，不改变存量 ID 或使旧密文失去读取路径。
- 本文交付 PRD；不包含生产代码改造、真实部署、正式发布时间或未经评估的人日承诺。
