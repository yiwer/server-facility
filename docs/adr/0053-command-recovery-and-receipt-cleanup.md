# ADR-0053: Keep command identity after uncertain delivery and receipt cleanup

Accepted. 2026-10-04. Ticket30, FR04, AC05/06. Extends ADR0052; it does not replace its transaction, fingerprint, current-authorization or capacity policy. Execution evidence is recorded separately from this decision.

Receipt availability and command identity have different lifetimes. V4 clears only the original result's note ID, slug, title and body; the complete command identity, fingerprint, expiry and lifetime charge remain. A cleared note ID permanently means410 for an authorized matching retry, even if a later clock comparison appears unexpired. Authorization still precedes fingerprint conflict, which precedes expiry. An ordinary replay SELECT sees one coherent committed receipt row; it needs no separate lease or replay row-lock protocol.

The application owns one private PostgreSQL maintenance function with an explicit finite cutoff no later than the database's current clock and a batch of1–1000. One atomic UPDATE clears eligible receipts selected with FOR UPDATE SKIP LOCKED and joined by their complete primary key. A partial expiry index covers receipts still present. A zero count can mean candidates are locked and does not promise global exhaustion. The batch bounds modified rows; it does not bound index work or elapsed time by itself.

The migration binds the function and target table to the actual Flyway application schema, preserving non-public deployments and preventing temporary-table shadowing. The function is VOLATILE, PARALLEL UNSAFE and SECURITY INVOKER, with PUBLIC execution explicitly revoked. The migration owner or an explicitly granted operations role calls it using its own table privileges. There is no elevated definer identity, background scheduler, HTTP maintenance endpoint or runtime schema selector.

The dedicated caller completes separate statement_timeout5s and lock_timeout500ms settings before its autocommit SELECT, with finite connection/read/cancellation budgets. A PostgreSQL function-local SET cannot reliably arm the current top-level statement's timer; querying a setting does not prove that timer is running. The function therefore validates its data parameters and leaves these operational preconditions explicit. Each batch commits independently. A transport timeout leaves commit outcome uncertain; retrying the same cleanup safely counts only receipts it still clears.

The business guarantee is one committed effect within the declared PostgreSQL transaction and retained identity. An HTTP disconnect, process death, timeout or commit exception alone cannot establish non-commit. Consumers retain the same key and command across recovery and recheck current permission; they must handle permanent receipt expiry. External non-transactional side effects need their own application protocol. This decision introduces no cross-system exactly-once claim.

The recovery fixture runs the actual application, Security, Flyway, Notes and JDBC transaction manager in independent JVMs with the ordinary facility jar. Test-only connection proxies gate a specifically correlated HTTP operation immediately before real Connection.commit or after it returns. Separate response gates establish actual partial delivery. These tests are distinct from the existing independently built executable-jar consumer, and fixture feasibility alone is not business acceptance.
