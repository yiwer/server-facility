## Diagnosis and limits

The public CI14 annotation showed `LocalDatabase` startup failure, then `TemplateConsumer` replacing it with a cleanup assertion. Native PostgreSQL logs were not archived because the archive operation followed the failing cleanup assertion. Thus the available annotation could not establish the native startup cause.

PostgreSQL18.6 source establishes a concrete platform difference: direct server startup rejects a Windows administrator token, while `pg_ctl start` uses its Windows restricted-process implementation. The JUnit fixture already used pg_ctl and passed on CI14, whereas the developer CLI directly launched postgres. This is the leading CI14 hypothesis, not a claim that the unavailable Windows postgres.log was read. The local process was checked with WindowsPrincipal.IsInRole(Administrator)=false; no local elevated-token reproduction is claimed. References: [server check_root](https://github.com/postgres/postgres/blob/REL_18_6/src/backend/main/main.c), [pg_ctl start_postmaster / CreateRestrictedProcess](https://github.com/postgres/postgres/blob/REL_18_6/src/bin/pg_ctl/pg_ctl.c).

A public-process regression now records `postgres -D <owned data> -C port`: the native program reads configuration and exits without starting a server. On a normal token it succeeds; on a Windows administrator token it must emit the specific administrator refusal. In the same process environment, the actual CLI has already completed two pg_ctl-managed starts/stops. CI15 can therefore supply the missing controlled platform comparison; other direct-executable failures are not accepted.

Forced OS termination cannot run Java hooks; the README documents explicit pg_ctl recovery rather than promising automatic recovery from arbitrary kill.
