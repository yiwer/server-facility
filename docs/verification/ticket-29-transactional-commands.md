## Contract and ownership

POST/PUT require exactly one `Idempotency-Key`, 1–128 ASCII letters/digits/dot/underscore/colon/hyphen. Direct Module calls take the same explicit key. Workspace/verified issuer+subject/fixed operation/key form the identity. Versioned SHA-256 fingerprints use four-byte big-endian UTF-8 byte lengths and preserve validated values exactly; update includes its target UUID. JSON member ordering does not change the command, while content, whitespace and Unicode differences do. The application neither truncates nor normalizes identities.

Each issuer/subject has a65536 UTF-8 byte storage budget; NUL and unpaired surrogates fail before JDBC. V3 preserves eligible old text and migrates membership's potentially oversized text B-tree identity to a bounded digest plus complete-tuple checks. An existing V1/V2 identity above the new finite budget is an explicit migration precondition failure, with an aggregate-only audit query and owner-controlled transition policy in COMMANDS.md. It is never silently truncated, normalized, rebound or discarded. A real65537-byte legacy identity causes transactional V3 rejection while preserving its exact text and V1/V2 history without half-migrated objects. PostgreSQL18.6 actually declares convert_to STABLE, so a private trigger computes the value instead of a falsely IMMUTABLE function/generated expression. Collision checks fail closed rather than authorizing another tuple.

Writes explicitly select READ COMMITTED, rejecting an ambient transaction rather than silently joining it or using REQUIRES_NEW. A losing INSERT ON CONFLICT performs a separate SELECT after the unique-index wait. Current membership is checked both before claim and again after waiting, before receipt/conflict/expiry disclosure. Pagination retains its own repeatable-read snapshot. Permission is observed at these checks; the contract does not cancel a request whose permission changes after its last check.

Business effect, identity, successful-command charge and original receipt commit atomically. Replays retain original201/Location or200, including after later editing/deletion. New keys at the workspace's10000 lifetime command capacity return429 without Retry-After; successful replay/read/revoke remain available. Rollbacks and refusals leave no successful identity/charge. Capacity is per workspace, not a whole-database bound; workspace admission remains deployment policy.

The finite unique-claim lock timeout produces409 `command_processing` and Retry-After1. Ordinary table ROW EXCLUSIVE and the sole workspace FK KEY SHARE lock are acquired outside this claim-only exception mapping; unrelated table/FK timeouts remain503. These compatible PostgreSQL locks do not add an advisory lock layer or serialize command_count non-key updates. Database/connection/query failures503 and unexpected persistence faults500 retain safe generic details. Neither a timeout nor a disconnected response proves non-commit. The application does not automatically repeat a transaction in-process. Receipts expire24h after their result write, returning410 while identities remain reserved; actual physical cleanup and exact commit-point process-loss/dual-JVM recovery are owned by30.
