# Upgrades and delivery

The application is owned source code. Its Maven version is independent of the template revision in [template-origin.properties](template-origin.properties) and the runtime dependency in `pom.xml`. `secured-api` revision `2026.10.0` uses the Boot 4 / Jackson 3 development line `cn.code91:server-facility:0.2.0-SNAPSHOT`. A SNAPSHOT coordinate is mutable; record the actual resolved ordinary jar SHA-256 for every delivered build.

Before copying, record `git rev-parse HEAD` and `git rev-parse HEAD:templates/secured-api` in the source checkout. Keep those exact identities beside the delivered application, together with the ordinary library jar and executable application jar checksums, JDK/OS, Wrapper version, and build commands. The marker intentionally contains no self-referential Git hash. Copying does not require Git at application runtime.

For an upgrade, work on a clean application branch and compare the previous exact template tree with the intended tree. Review a small patch for the affected configuration, source and tests. Apply it only after verifying its source revision and file preimages. If an affected file contains custom edits, perform a manual three-way review; never regenerate over the application, use partial `--reject` application, or infer compatibility from a matching SNAPSHOT name. Preserve business source, tests and unrelated configuration; run those tests before and after and retain the diff. Apply configuration and database migrations explicitly. Existing deployed Flyway migrations are immutable.

The documented historical demonstration uses development commits `4a5ad5d2513ccf7d87f2feeb95056551b4b0ef15` → `307dae62ea63fce19c1630dfaf0fa0b811869a71`. Its three-file template patch requires integral JDBC query budgets of 1–3 seconds. An old `1500ms` setting actually became 1 second; the sample explicitly chooses `1s`, preserving that effective budget. The patch leaves its historical runtime unchanged and does not upgrade arbitrary prior applications to this template revision. Later Notes command and receipt migrations require their own [command preflight](COMMANDS.md).

The current candidate also requires `spring.datasource.hikari.maximum-pool-size` in2–16. Earlier development copies accepted1, but that configuration cannot complete this template's fixed Flyway/PostgreSQL migration path, which needs two connections from the same controlled pool. It now fails the safe application-policy check before migration connection acquisition. Review an existing setting of1 and explicitly select an appropriate size of at least2; the default remains4 and the acquisition timeout remains1000ms. No separate Flyway datasource or automatic timeout increase is introduced. This correction does not rewrite the frozen historical demonstration or establish a cause for the separately retained default-pool timing failures.

## Verification and environment

JDK 25 and the checked-in Maven 3.10.0 Wrapper are required. Library `java verification/Verify.java fast` requires no database and runs runtime tests, architecture, coverage and dependency checks. The copied application's `./mvnw clean verify` is the full application gate: it needs PostgreSQL 18.6 native tools on `PG_BIN`, ephemeral loopback ports and filesystem access. It tests actual HTTP, authentication and persistence, and packages the executable jar. No Docker or external identity account is required. See [the application run commands](README.md).

Production deployment is an application-owned operation. Build and verify first, retain the jar checksum, configure PostgreSQL and the issuer, then start the exact jar. Use `SPRING_PROFILES_ACTIVE=prod`; configure `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`, `SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_ISSUER_URI`, `SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_AUDIENCES`, and `APP_SECURITY_RESOURCE_URI`. Optional direct key discovery uses `SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_JWK_SET_URI`. Supply secrets through the deployment environment's protected mechanism. The local profile is only for disposable development. The [README](README.md) specifies bounded JDBC settings, trust and readiness behavior; [observability](OBSERVABILITY.md) defines application logging, sampling and export policy.

Back up application data and validate migration privileges before a schema change. Keep the same issuer and database across a restart to retain identity and business data. A successful `/health` response does not establish that every dependency is reachable. Use readiness plus an authenticated business operation. Stop through the deployment platform's normal JVM shutdown mechanism and retain shutdown diagnostics. This source delivery does not deploy an application or promise schema rollback.

## Runtime migration boundary

The original Boot 3 / Jackson 2 development line retains `0.1.0-SNAPSHOT`; the new Boot 4 / Jackson 3 line uses `0.2.0-SNAPSHOT`. Applications must recompile and migrate public Jackson imports, mapper ownership and changed factory signatures. Retained methods may have explicit safer behavior or finite budgets. Source, binary, HTTP/wire and persisted-data compatibility require separate evidence. The source repository's `docs/building/runtime-migration-ledger.md` indexes the 29 packages and their actual consumer evidence. Neither line is published by this change. Unknown private/source consumers remain outside the known inventory; no unsupported sunset date or maintenance promise is implied.
